SYSTEM ARCHITECTURE
--------------------------------------------------

[ Binance WS ] ===(wss://fstream.binance.com/market/ws)===> [ priceStream.js ] (0 cost, 1s tick)
                                                               |
                                                               v
[ Binance REST ] <---(HTTP GET / pLimit)--- [ Node/Express cronJobs.js ] <---(Socket.io)---> [ React Frontend ]
                                                               |
                                                               v
                                                      [ SQLite (WAL Mode) ]
                                                               |
                                                               v
                                                    [ Telegram & Gemini AI ]

Architecture Flow:
1. priceStream.js maintains a single persistent WebSocket to Binance Futures market stream, maintaining a sub-second in-memory live price cache of all USDT perpetuals for zero API weight cost.
2. cronJobs.js wakes up every 5 minutes and calls Binance REST via binanceBreaker (Circuit Breaker) for the Top 150 pairs.
3. It fetches 15m and 1h candlestick data in batches using a concurrency limiter (pLimit) to prevent rate limit limits.
4. The data is fed into SignalScoringEngine.js.
5. The Engine scores each pair using statistically decorrelated weights, volume Z-scores, and ATR-based dynamic TP/SL levels. Ranging markets are skipped entirely via the ADX regime filter.
6. Signals matching settings.minScore are instantly persisted to SQLite database (optimized with WAL mode + Normal sync to prevent write contention) and high-confidence signals are validated by Gemini AI via geminiBreaker.
7. The Backend broadcasts the new signals via Socket.io to the Frontend.
8. The Backend sends Telegram alerts for signals with Score >= 75.
9. Every 5 seconds, cronJobs.js evaluates active database signals against the local WebSocket price cache (zero API calls).
10. If TP/SL is hit, the database marks the signal as WIN/LOSS and updates the Win Rate on the frontend.

API ENDPOINTS
--------------------------------------------------
1. GET /api/meta
   - Returns basic server health and version info.
2. POST /api/scan
   - Manually triggers a fresh Binance market scan.
3. GET /api/signals
   - Returns the latest signals from the cache.
4. GET /api/signals/history
   - Returns all closed historical signals.
5. GET /api/system-notes
   - Returns project documentation contents.
6. GET /api/settings & POST /api/settings
   - Fetches and updates dynamic AI engine weights.
7. GET /api/health
   - Verifies Binance API, SQLite, Telegram, and Gemini status, including Circuit Breaker states.
8. POST /api/telegram/broadcast
   - Broadcasts a custom HTML announcement to Telegram channels.
9. GET /api/logs & DELETE /api/logs
   - Fetches and clears persistent SQLite system exceptions and logs.
10. POST /api/logs/test
    - Simulates a diagnostics system exception for testing.
11. POST /api/webhook
    - (Production only) Receives incoming messages from Telegram.

DATABASE TABLES (SQLite)
--------------------------------------------------
Table: signals
Stores every high-confidence trading signal to track its performance.

Columns:
- id (Primary Key, format: SYMBOL_TIMESTAMP)
- symbol (e.g. BTCUSDT)
- direction (LONG or SHORT)
- score (0 to 100)
- confidence (LOW, MEDIUM, HIGH, VERY_HIGH)
- entry (Price at time of signal)
- tp1, tp2, stopLoss (Calculated price targets)
- status (ACTIVE, WIN_TP1, WIN_TP2, LOSS_SL, EXPIRED)
- createdAt, closedAt (Unix timestamps)
- maxProfitPct (Maximum profit percentage achieved)
- reasons, subScores (JSON strings of engine data)

Table: settings
Stores dynamic AI Engine weights and configuration limits.
Columns:
- key (Primary Key, e.g., "emaAlignment")
- value (e.g., "0.25")

DEPLOYMENT PROCESS
--------------------------------------------------
1. Clone repository to VPS.
2. Run `npm install` to install dependencies (compiles better-sqlite3).
3. Copy `.env.example` to `.env` and fill in keys.
4. Run `npm run build` to compile the Vite frontend into the `/dist` folder.
5. Use PM2 to run the server in production: `NODE_ENV=production pm2 start server/index.js`
   (In production, Express serves the API on port 8080 AND serves the frontend UI from `/dist` on the same port).
6. Configure Nginx reverse proxy to point to port 8080 and attach SSL.

KNOWN ISSUES & PRODUCTION WORKAROUNDS
--------------------------------------------------
- Binance IP Rate Limits: If the scan frequency is too high or the batch size too large, Binance returns HTTP 418 (IP Banned). Mitigated by 5-min intervals and 150-pair limits.
- Hostinger Node Version ABI Mismatch: Node major version updates can mismatch better-sqlite3's C++ bindings (e.g., compiled on NODE_MODULE_VERSION 115 but run on 137). Resolved by performing a complete Node rebuild/reinstall (`rm -rf node_modules package-lock.json && npm install`) on the production VPS.
- Binance Legacy WS Stream Drop: Connecting directly to legacy stream paths (e.g. `fstream.binance.com/ws`) accepts connection handshakes but silently drops all message events. Bypassed by updating to the newly required routed market path: `wss://fstream.binance.com/market/ws/!miniTicker@arr`.

1. PRODUCTION WS FIX: Legacy WebSocket connection string `wss://fstream.binance.com/ws/!miniTicker@arr` successfully connected but returned zero data due to Binance stream deprecation. Upgraded connection endpoint to the modern routed URL: `wss://fstream.binance.com/market/ws/!miniTicker@arr`.

Enhanced the Zustand frontend client socket handler with nullish coalescing to prevent fallback errors when `totalPairs` is `0`, and set `scannedAt: null` on purge so that the dashboard pristine state reads `Last scan: Never` and `0 pairs` beautifully.

5. AUTO-CLEANUP ON STARTUP: Integrated startup SQLite cleanup targeting EXPIRED signals older than 7 days, preventing database bloat and keeping indexes hot.
6. DAILY CLEANUP CRON SCHEDULE: Added a daily cron job scheduled at 03:00 AM in `cronJobs.js` to execute `deleteExpiredSignals(7)` continuously.
7. DUPLICATE ACTIVE SIGNAL GUARD: Modified `insertSignals` in `database.js` to dynamically reject insertions for symbols that already have an active trade open, preventing whipsaw and spam alerts during high volatility.
8. EMPIRICAL WIN-RATE LOOKUP: Integrated real-time 30-day historical win-rate calculation inside `insertSignals` (`getSymbolWinRate`). Automatically scans preceding resolved trade statistics for a specific symbol & direction to attach empirical win rates and sample sizes to incoming active signals for high-confidence trading.
9. 4H MULTI-TIMEFRAME TREND CONFLUENCE: Integrated a high-order 4h trend filter in `SignalScoringEngine.js` using EMA(9)/EMA(21) alignments and EMA(200) prices. Dynamically filters out short-term counter-trend signals to eliminate whipsaws and elevate edge.
10. PM2 PRODUCTION DAEMON ECOSYSTEM: Added custom `ecosystem.config.js` to manage process lifecycles, memory boundaries (512MB), graceful shutdown (5s), structured system logging `/var/log/signal-scorer/`, systemd boot survivability, and configured public listener to use PORT 9000 to match VPS Nginx reverse proxy firewall rules.
